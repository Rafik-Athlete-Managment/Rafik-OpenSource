# Frontend audit instructions

Use this prompt for a new audit or a review of a frontend change. The [frontend reference](../reference/frontend/README.md) is the maintained inventory; the [design system](../DESIGN_SYSTEM.md) remains the visual specification.

## Improved prompt

Audit the entire Rafik web frontend against the current single-institution product. Produce a complete, traceable development reference and fix confirmed obsolete code, duplicate implementations and broken navigation. Preserve working institutional features, server authorization, recoverable drafts, exact command replay, localization and account/file lifecycle compatibility.

1. **Establish scope and evidence.** Read root AGENTS.md, CONTRIBUTING.md, requirements, architecture, current ledger, design system and verification. Inventory the checked-in frontend source, actual router declarations, shell navigation, embedded screens, dialogs and data-driven links. Distinguish source findings, rendered observations and unverified assumptions. Android is separate unless explicitly included.
2. **Document every view.** Record its name, repository path, owning folder, URL or embedded parent, purpose, institutional value, router gates and server-enforced role/resource restrictions. Include incoming and outgoing navigation, query-driven modes, actions that open another view and external/token/notification entry points. Identify where multiple routes intentionally reuse one implementation.
3. **Document every local component.** Record its name, path, purpose, direct rendered consumers and all consuming views, including transitive use. Cover the application shell and domain components as well as shared controls. Do not mistake an unused import for a rendered consumer. Summarize external UI libraries without copying their implementation inventories.
4. **Trace navigation in both directions.** Compare navigation destinations with the real router, aliases, redirects and conditional build routes. Follow variable/computed links, notification destinations and setup/invitation flows into the backend when necessary. Provide readable Mermaid overview and detailed workflow maps, plus an adjacency reference with evidence. A missing sidebar link alone does not make a route orphaned: token links, detail/edit pages, guard recovery, compatibility aliases, development tools and the not-found handler may be intentional.
5. **Classify before deleting.** For each suspicious item, record whether it is supported, shared, an intentional compatibility boundary, duplicated, obsolete or genuinely unreachable. Explain the call paths and current product requirement. Consolidate verified duplicates into the existing appropriate implementation. Remove obsolete UI/routes and their exclusive helpers/tests; repair live links. Do not delete historical data, migration history, private-file cleanup, account exports or supported mobile/API contracts merely because the corresponding old web screen was retired. Any destructive data change needs an explicit forward-migration plan.
6. **Verify the changes proportionately.** Use a repeatable inventory check for coverage, rendered component references and route targets. Run focused type/unit/build checks and the smallest affected browser/API journeys. Use disposable fixtures and clean only their artifacts. Where a rendered review is performed, state browser, viewport, locale, theme and states actually inspected. Do not claim whole-product visual or security acceptance from a source graph.
7. **Keep one maintained reference.** Store human-readable Markdown under docs/reference/frontend/, with relative source links and clear maps. Keep the reusable prompt in docs/development/. Link every maintained document from docs/README.md. Generate mechanical catalogs from source plus reviewed semantic descriptions; provide a check command that detects drift. Update architecture, maintainer guidance, changelog, ledger and verification in the same change.
8. **Report results.** Give exact inventory counts, findings by priority, changes/removals and reasons, commands and outcomes, retained compatibility boundaries, remaining gaps and the reviewable PR. Do not describe a proposal as implemented or an unrendered screen as visually validated.

Work on the current approved topic branch and keep the release PR unmerged. Ask only when a consequential product decision cannot be resolved from existing requirements; continue independent inventory work while awaiting an answer.
